# План аудита и доведения Ксении до повседневного использования

Дата: 7 сентября 2026 года. Исходный локальный commit: `e22681f`.

Статус: план после первичной инвентаризации, а не свидетельство готовности релиза.
Рабочая конфигурация, модели и компоненты при подготовке плана не менялись.
Полный новый аудит всех файлов и физическая приёмка ещё не выполнены.

## 1. Цель и границы

Сохранить существующий фундамент, но обеспечить предсказуемый пользовательский путь:

- один запуск и одна фраза «Ксения слушай» открывают разговор;
- после ответа, ошибки поиска и отказа инструмента разговор продолжается без новой активации;
- UI-Mate остаётся собеседником, пока Agents-A1 выполняет фоновое исследование;
- Fast/Thinking имеют единый понятный смысл в голосе, меню и исследовании;
- имя, пути, устройства, память и разрешения принадлежат конкретной установке;
- другой человек получает чистую установку, а не копию окружения владельца проекта;
- готовность подтверждается сквозными сценариями, а не одним числом unit-тестов.

Не обещать абсолютное отсутствие ошибок. Требовать ограниченного времени отказа,
сохранения данных, понятного сообщения и проверяемого восстановления.
Не переписывать проект на другой framework. Не подменять реальное действие фразой об успехе.

## 2. Что установлено при первичном просмотре

Источники: текущие исходники, merged-настройки, lock-файлы, метаданные установленного
Python-окружения, последние локальные журналы и документы. Старые benchmark-цифры
сохраняют свою дату; они не являются новыми измерениями 7 сентября.

- В `src`, `scripts`, `tests`, `config`, `procedures`, `web`, `requirements` найдено
  178 файлов командой `rg --files`. Это инвентарь этих каталогов, не покрытие аудита.
- Быстрая пара назначена правильно: `assistant → ui_butler`,
  `researcher → research_fast`. Отдельные процессы двух моделей не означают
  независимое исполнение разговорных и исследовательских задач.
- Фактические merged-настройки: `live.enabled=false`, `speech_barge_in=false`,
  `live.audio_processing.enabled=false`, `voice.playback_backend=system`.
- Существуют `AudioCaptureService`, Live state machine, streaming TTS,
  generated/spoken memory, AEC-адаптер, performance harness, стабильный snapshot
  tool schemas, отменяемое HTTP-чтение и Permission Broker. Их не нужно создавать заново.
- Последний полный сохранённый gate от 2 сентября: 447 тестов и shuffled-прогоны,
  активный UI-Mate, HTTP cancellation, LAN, Silero→Whisper. RAG пропущен как выключенный.
  Это не доказывает непрерывный Live, фоновый разговор или чистую установку на другом ПК.
- На момент read-only проверки процессов `llama-server`, `python`, `pythonw` не найдено;
  серверы и микрофон для подготовки плана не запускались. На D свободно около 40 ГБ:
  обновления нужно планировать с учётом staging и резервных копий.

## 3. Порядок выполнения и контрольные точки

Каждый этап: воспроизводимый сценарий → регрессионный тест → минимальный diff →
соответствующая живая проверка → полный gate при изменении кода → документация → checkpoint.
Не совмещать обновление runtime, изменение маршрутизации и переработку аудио в одном diff.

### Этап 0 — P0. Полная карта и воспроизводимый исходный результат

1. Включить в реестр не только Python: root CMD, PowerShell, JSON, процедуры, web,
   CI, установщик, release manifest, ярлыки, документацию и зависимости.
2. Для каждого файла отметить: назначение, входы/выходы, владельца состояния,
   вызывающие/вызываемые компоненты, настройки, обработку ошибок, тайм-ауты,
   cancellation, security boundary, тесты и статус фактического чтения.
3. Разделять `REVIEWED`, `NEEDS_TEST`, `BLOCKED`, `NOT_APPLICABLE` и `NOT_REVIEWED`.
   Наличие файла в списке не выдавать за проверку каждой строки.
4. Снять git/base commit, версии и хеши runtime, доступные устройства, ресурсы,
   effective-настройки и состояние собственных процессов. Не публиковать ключи и запросы.
5. До изменений сохранить приватные checkpoint-копии user config и постоянных данных;
   для живой SQLite использовать backup API либо согласованную остановку.
6. Сначала повторить отказ пользователя в Fast и следующий ход той же сессии.
   Отдельно прогнать текущий full gate; явно указать skipped и неполные traces.

Результат C0: реестр покрытия аудита, исходные воспроизведения, таблица версий,
безопасный снимок состояния и проверяемый способ возврата.

### Этап 1 — P0. Ошибка задачи не разрушает разговор

- Разделить успешный результат, отказ политики, отказ пользователя, отмену,
  невалидный вызов модели, временную сеть, недоступную модель и фатальную среду.
- Завершать конкретную задачу и освобождать её ресурсы ровно один раз.
- Невалидный JSON не доходит до executor. Допустим ограниченный запрос исправления
  формата модели; после исчерпания бюджета — понятный отказ задачи, не конец сессии.
- Nonzero exit code инструмента — структурированный результат, а не авария приложения.
  Не запускать unsafe host ради этого теста: интеграция с реальным кодом ждёт sandbox.
- Повторять только безопасные операции. При неизвестном результате записи/отправки
  не повторять действие автоматически и не заявлять rollback.
- Сетевому исследованию дать общий deadline, бюджет попыток и отменяемые ожидания.
  Не говорить «уточните запрос», когда действительно недоступна сеть.
- Сохранить sanitised diagnostic ID и краткую человеческую причину. Не озвучивать traceback.

Файлы: `cli.py`, `agent.py`, `orchestrator.py`, `tasking.py`, `research.py`,
`browser.py`, `user_messages.py`, соответствующие tests.

Приёмка C1: в одной сессии последовательно вызвать timeout, malformed tool call,
отказ разрешения и cancellation; после каждого следующий простой вопрос работает.
Не осталось занятого task lock, хвоста озвучивания, чужого approval или reader thread.

### Этап 2 — P1. Универсальность и единая политика режимов

- Разделить личность Ксении, профиль человека, возможности установки и каталог моделей.
- Необязательное имя спросить при первом запуске; без имени использовать «вы»/«Пользователь».
  Сохранить имя нынешнего владельца в личных настройках при миграции; не переписывать память.
- Проверить все источники prompt: system, роли, tool descriptions, процедуры,
  summary, research instructions, временные статусы и голосовые подтверждения.
- Не удалять авторство проекта или исторические протоколы ради запрета хардкода.
  Семантические роли, настраиваемые пути и параметры отличать от необходимых
  protocol constants, строгих security limits и закреплённых SHA-256.
- Исправить разбор Fast/Thinking, проверить совпадение меню, голоса и уже открытой сессии.
  Новая настройка применяется с понятной границы следующего запроса, не посреди задачи.
- Режим задаёт конфигурационные бюджеты рассуждения/токенов/исследования, а не имя модели.
  Явный запрос глубокого исследования может получить больший бюджет с коротким пояснением.
- Контекст для reviewer должен соответствовать обсуждаемой задаче; приватные рассуждения
  не озвучиваются и не подменяют доказательства из инструментов.

Приёмка C2: установки без user.json и с разными именами; обновление сохраняет личное;
цитата «включи Thinking» не меняет режим; выключение работает; все входы показывают
одинаковое состояние; Fast-поиск не получает скрыто normal/deep бюджет.

### Этап 3 — P0. Непрерывный Live как обычный пользовательский режим

Не сводить изменение к `live.enabled=true`: исправить жизненный цикл сессии.

1. Разделить ожидание активации, активный разговор, временную неисправность устройства
   и явное завершение разговора. Обычная пауза и завершённый ответ не завершают сессию.
2. После активации принимать следующие реплики как в тишине после ответа,
   так и при поддерживаемом full duplex во время ответа/работы.
3. Сохранить единственного владельца микрофона и bounded PCM buffers.
   Проверить потерю кадров, медленного подписчика, переподключение и Bluetooth device switch.
4. Согласовать PCM output, AEC far reference, VAD и turn detector;
   отказ AEC/вывода не маскировать неподконтрольным SAPI.
5. Разделить остановку озвучивания, отмену текущего разговорного ответа и отмену
   фоновой задачи. Не отменять исследование только потому, что человек начал другую реплику.
6. Зафиксировать понятные команды: «замолчи», «отмени поиск», «закончи разговор».
   Для неоднозначного «стоп» немедленно остановить речь и безопасно уточнить область задачи.
7. Не записывать generated text как услышанное. Сохранить существующий консервативный
   spoken-prefix контракт; точность до каждого слова не обещать без playback alignment.
8. Проверить паузы 1–2 секунды, самокоррекции, английские названия и ложные wake/stop от TTS.
9. После успешных программных и физических сценариев включить непрерывный Live default.
   Для неподдержанного full duplex предложить явный ограниченный режим без одновременного
   слушания во время TTS, но с продолжением разговора после ответа. Не называть его full duplex.
10. Показать и озвучить состояние слушания; завершение разговора возвращает только wake.
    Полное выключение микрофона должно быть отдельно доступно и не означать «wake ещё слушает».

Файлы: `cli.py`, `live.py`, `audio_capture.py`, `wake.py`, `stt.py`, `speech.py`,
`turn_detection.py`, audio/STT/TTS workers, tests и пользовательская инструкция.

Приёмка C3: 30 последовательных ходов после одной активации, включая ошибки,
перебивания, тишину и смену устройства; затем длительная сессия с периодами простоя.
Физически проверить Tour One M3 и Sense Pro по доступности, отдельно тракт с реальным эхом.
Нет самоперебиваний, потери начала речи и неограниченного роста очередей/памяти/threads.

### Этап 4 — P0/P1. UI-Mate разговаривает, Agents-A1 исследует

Целевая связь, а не обещание уже реализованной функции:

```text
активная разговорная сессия → UI-Mate → единый диспетчер озвучивания
             │                                  ↑
             └→ очередь фоновых задач → Agents-A1 → событие результата
```

- Первый объём: один разговор + одна фоновая read-only research-задача.
  Не вводить сразу неограниченный multi-agent framework.
- Принятую задачу сначала надёжно зарегистрировать и только потом сказать
  «Поиск запущен. Пока могу ответить на другой вопрос». Отличать queued от started.
- У задачи свои ID, snapshot запроса/контекста, TaskControl, ToolExecutor,
  approval scope, local-data exposure state и deadline. Общие mutable session/tools
  нельзя просто вызывать из двух threads.
- Историю разговора изменяет один координатор. Фоновый результат приходит событием,
  дедуплицируется по task/result ID и сохраняется отдельно от услышанного текста.
- Единственный диспетчер речи: слушание человека и подтверждения важнее статусов;
  результат поиска не перебивает реплику, не говорит поверх другого ответа и не теряется.
- «Что нашла?», «подожди», «отмени поиск», новая тема и уточнение поиска имеют явные переходы.
- Thinking-консультация и поиск конкурируют за Agents-A1: нужна ограниченная очередь
  и честный статус, а не скрытое зависание UI-Mate или запуск третьей копии модели.
- При переходе к primary удерживать ресурсную резервацию до завершения/паузы
  resident jobs. Не выгружать модель из-под активного запроса. Не обещать одновременное
  проживание пары и тяжёлой модели без замера полного VRAM бюджета, включая STT/KV.
- Не удалять глобальную блокировку без замены scoped locks и тестов.
  Одноразовый доверенный допуск должен остаться привязан к одному запросу; фоновая
  задача не получает разрешения от текущей реплики «да». Решение оформить в DECISIONS
  и повторно проверить против инвариантов AGENTS/SECURITY до реализации.
- После reboot/crash сохранять состояние и результат. Внешние действия не повторять
  автоматически; для v1 допустимо честное interrupted + предложение продолжить.

Приёмка C4: реальный поиск продолжается во время трёх обычных разговорных ходов;
его ответ поступает один раз в безопасный момент. Проверить ошибку/отмену одной
задачи, поздний callback, конфликт режима, отказ resident и попытку permission leakage.

| Browser | Playwright 1.62.0 | Совместимый Chromium, поиск/read/interact отдельно, SSRF/redirect, отмена и чистая установка |
| Остальные пакеты | `requirements/*.lock.txt`, runtime-assets lock | Полный dependency inventory, транзитивные зависимости, лицензии, уязвимости, hashes |

7 сентября официальная страница [llama.cpp releases](https://github.com/ggml-org/llama.cpp/releases)
показывала вверху `b10834`, помеченный **Pre-release**. Это кандидат для анализа,
не автоматически выбранная рабочая версия. PoolSide сверять с
[его собственной веткой laguna](https://github.com/poolsideai/llama.cpp/tree/laguna),
не подменять официальным runtime. Конкретные целевые версии выбираются после changelog,
совместимости и security-проверки; наличие большей версии не доказывает пользу.

Порядок: исправленный regression baseline → official runtime → PoolSide → browser →
voice/STT → прочие зависимости. Критическая подтверждённая уязвимость может изменить порядок.
Для каждой группы отдельно: candidate manifest, SHA-256, staging, benchmark, full gate,
установка, проверка обратного отката и checkpoint. Проверить, что updater/rollback
восстанавливают именно resident-пару и все services, а не только старый primary.

Не менять драйвер, firmware, CUDA toolkit или рабочую venv попутно. Не скачивать
веса ради инвентаризации. Текущие загрузки не прерывать. Проверять свободное место
для двух состояний среды и резервной копии до начала скачивания.

Приёмка C5: повторная установка из lock воспроизводится; откат возвращает прежние
версии и пользовательский путь без потери settings, памяти, workspace и выбранного режима.

### Этап 6 — P1/P2. Скорость и качество на реальных задачах

- Использовать существующий performance harness. Добавлять лишь недостающие
  milestones: принятие/очередь фоновой задачи, model lease wait, доставка результата.
- Измерять отдельно cold/warm, voice_end→STT, STT→первый аудиоответ,
  очередь→начало работы, retrieval/network/prompt evaluation/generation/TTS/playback.
- Проверить стабильный prefix и tool schemas на одинаковых последовательных ходах.
  Не пересоздавать context ради каждой Live-команды и не снижать long-context ceiling.
- Убрать из общего маршрута подтверждённые частные костыли под один вопрос/город/владельца;
  не заменять их десятками новых if-веток. Сохранить типизированные быстрые навыки,
  когда они честно решают целый класс задач, например время и погоду.
- Настраивать phrase segmentation/буфер Silero по TTFA и естественности;
  ударения/ё/омографы проверить на corpus, а не объявлять решёнными по включённому флагу.
- Не делать фиксированную замену омографа без контекста. Пользовательский словарь
  произношения допустим как слой предпочтений, не как универсальная замена движка.
- STT: реальные короткие команды, длинная речь, имена, пути, английские модели,
  шум, паузы и самокоррекции; сначала небольшой постоянный corpus, затем 100–300 фраз.
- RAG: проверить фактическое включение, индекс, stale files и no-match; измерить
  Recall@k/MRR/nDCG/полезность. Conditional reranker принимать только по качеству и задержке.
- MTP/DFlash менять только после реального bottleneck; использовать уже выполненные
  замеры как исторический ориентир, не повторять большой model contest вместо исправления UX.

Приёмка C6: воспроизводимый before/after corpus, p50/p95, число ошибок и стоимость
ресурсов. Малый diff без выигрыша или с ухудшением правильности не принимать.

### Этап 7 — P1/P2. Безопасность и фактические возможности

- Production sandbox остаётся обязательным до обещания автономного исполнения кода.
  Повторно проверить prerequisites текущего ПК, не считать августовское состояние вечным.
- Сравнить пригодные Windows-варианты по реальной изоляции FS/network/process/UI и
  ресурсам. Job Objects сами по себе не заменяют файловую/сетевую границу.
- Профили offline/networked, явный network grant, scoped workspace, environment secrets,
  process-tree control, timeout и журнал должны проходить через Permission Broker.
- Проверять traversal, symlink/junction/reparse/TOCTOU, secret reads, SSRF/redirect,
  malformed payload, crash во время записи и утечку approval между задачами.
- UI-Mate: сначала правдивый ответ об экране по read-only capture; затем proposal→
  validation→Permission Broker→подтверждённый action. Не заявлять «вижу экран», если
  screenshot не передан, или «нажала», если инструмент не подтвердил действие.
- Проверить stale screenshots, DPI/multi-monitor, смену окна между proposal и action,
  финансовые формы и отказ неизвестного active window.
- В возможностях интерфейса различать «доступно», «выключено», «не установлено» и
  «экспериментально». Недоступный sandbox должен давать понятный отказ, не аварийный код.

Приёмка C7: negative-security corpus зелёный; необратимые реальные действия не делаются
ради проверки. До production sandbox профиль разработки с исполнением не считать готовым.

### Этап 8 — P1. Передаваемый релиз и пользовательская приёмка

1. Нейтральный первый запуск без редактирования JSON: выбор каталогов, проверка ресурсов,
   необязательное имя, автоматический микрофон с ручной коррекцией, понятный статус моделей.
2. Проверить все фактические ярлыки: начать/закончить разговор, микрофон, режим,
   инструкция пользователя, диагностика и обновление. Рабочие каталоги, кавычки,
   пути с кириллицей/пробелами и повторный запуск должны работать.
3. Установка под обычной новой учётной записью в чистой Windows, другой путь/диск,
   нет личного user.json, памяти автора, сохранённых аккаунтов и старой Python-среды.
4. Неполная загрузка, мало диска, отсутствующий интернет, чужой порт, повреждённый
   lock/config, отключённая гарнитура, sleep/hibernate/resume и повторный update.
5. Чётко отделить online bootstrap, офлайн-работу установленного ассистента и
   отдельный offline pack. Интернет-исследование не обещать без интернета.
6. Проверить manifest/hashes, licenses и отсутствие секретов, пользовательских логов,
   workspace и весов. Wheelhouse с hashes делать частью воспроизводимой поставки,
   а не скачивать неизвестные пакеты при обычном запуске.
7. Пройти путь целиком по пользовательской инструкции, только ярлыками/голосом/меню;
   отдельно клавиатура и screen reader. Разработческий shortcut не заменяет этот сценарий.

Приёмка C8: тестовый пользователь без истории проекта проходит первый запуск,
30-turn Live, фоновые новости + разговор, восстановление после ошибки, Fast/Thinking,
выход, повторный запуск, обновление и откат. Непройденная VM/физическая часть
остаётся явно непроверенной, а не зелёной по unit-тесту.

## 5. Обязательный сквозной набор

| Группа | Сценарии | Признак успеха |
|---|---|---|
| Старт | Чистый пользователь; один микрофон; два микрофона; нет микрофона; повторный ярлык | Понятное состояние, рабочий автовыбор/коррекция, нет второго владельца устройства |
| Разговор | Один wake, 30 ходов, паузы, новая тема, отсутствие имени, разные имена | Нет повторной обязательной активации, навязчивого представления, чужого имени |
| Ошибки | Network timeout/429, malformed JSON/SSE, model crash/OOM, tool nonzero, denied approval | Отказ ограничен задачей, следующий вопрос работает; причины различаются |
| Пара | Поиск + три реплики, Thinking во время поиска, результат во время человеческой речи | Задача не потеряна, диалог доступен, нет наложения TTS и ложного «готово» |
| Отмена | Перебивание, замолчи, отмени поиск, стоп при подтверждении, поздний callback | Остановлено нужное; unrelated job/approval не затронуты; нет повторной отправки |
| Акустика | Реальное эхо, оба JBL, тишина, шум, смена устройства, потеря far reference | Нет самоперебивания, скрытого SAPI, ложной spoken memory и потери первых слов |
| Ресурсы | Cold/warm, 30 ходов и длительный idle, остановка/смена моделей | Bounded queues/threads/RAM, нет leaked processes, конфигурация восстановлена |
| Безопасность | Escape/secret/SSRF/payload/approval leakage, crash при записи | Fail-closed, данные целы, секреты не журналируются |
| Восстановление | Crash/reboot/hibernate, pending job, update failure, manual config edit | Нет повторных внешних действий и потери личных данных; проверяемый rollback |
| Релиз | Чистая Windows/другой путь, manifest, доступность, инструкция | Пользовательский путь без помощи разработчика; пропуски перечислены явно |

Предварительные целевые бюджеты для обсуждения после baseline, НЕ текущие результаты:

- подтверждение принятия фоновой задачи — до 1,5 с после финального STT;
- простой тёплый локальный ответ — p95 до 3 с от конца речи до первого полезного аудио;
- остановка слышимого ответа — p95 до 300 мс от обнаружения перебивания;
- освобождение HTTP reader — до 1 с после запроса отмены;
- Fast-поиск — ограниченный общий бюджет, первоначально до 30 с до результата либо
  честного отказа; разговор при этом остаётся доступен;
- ноль зависших reader/worker после cleanup и ноль неконтролируемых повторов действий.

Записывать count/min/average/p50/p95/max, число отказов, полноту traces и cold/warm.
Не исключать тайм-ауты из результатов ради красивого p95. Малое число повторов
помечать exploratory, не выдавать одиночный smoke за статистику.

## 6. Quick wins и отложенные изменения

Небольшие отдельные diff после регрессионных тестов:

1. Правильное выключение Thinking и отрицательные тесты команд.
2. Нейтральные обращения и шаблоны без личного имени по умолчанию.
3. Правдивая причина сетевой ошибки и различение обычного транспорта/fallback в логах.
4. Актуальные статусы возможностей и исправление противоречий документации.

Непрерывный Live и конкурентный разговор/поиск НЕ quick wins. Простое снятие lock,
включение boolean или добавление thread не считается реализацией этих требований.

Оставить llama.cpp/PoolSide, собственный оркестратор/Permission Broker, Silero Xenia,
Playwright/UIA, SQLite/FTS5/embeddings/RRF и существующий performance/audio фундамент.
Не добавлять сейчас CrewAI, LangGraph, отдельную vector DB, native speech-to-speech,
MCP или десятки новых зависимостей. Крупные файлы делить только там, где требуется
ясное владение состоянием и доказуемая изоляция, не ради числа строк.

## 7. Документация, checkpoints и завершение

- Перед каждой рискованной фазой: commit исходного кода, приватный снимок настроек,
  версии/хеши runtime, состояния своих процессов, план отката.
- После неё: отдельный небольшой commit, regression evidence, дата/hardware/runtime,
  результаты и skips. Пользовательские данные и диагностические разговоры не публиковать.
- Существенные решения отражать в DECISIONS; поведение — в USER-GUIDE и
  ИНСТРУКЦИЯ-ПОЛЬЗОВАТЕЛЯ; состояние — в AUDIT/ROADMAP/HANDOFF; новые владельцы
  состояния — в ARCHITECTURE/SOURCE-MAP; миграции — в DATA-AND-MIGRATIONS.
- Не переносить историческое «проверено» на новый commit или другую гарнитуру.
  Для каждого release feature указывать AVAILABLE / DISABLED / EXPERIMENTAL / UNVERIFIED.
- В конце: полный `scripts/check.ps1`, shuffled order, dependency/release/Doctor,
  реальные разрешённые model/voice/browser/RAG/LAN gates и пользовательская серия.
  Обязательный пропущенный сценарий блокирует заявление о готовности этого профиля.
- Не стирать чужие изменения, runtime, workspace, модели и доказательства неудачных попыток.
  Откат кода не должен перезаписывать более новые пользовательские данные.

Ближайшее действие после согласования плана: C0 и C1 — восстановить точный Fast-сбой,
закрепить отрицательные сценарии и обеспечить продолжение разговора после отказа.
Затем C2/C3 и C4; обновления вести отдельными кандидатами, не отвлекаясь на новый конкурс моделей.
