# Обновление, восстановление и откат

## Политика версий

Ксения не обновляет критические компоненты до `latest` напрямую. Рабочая версия определяется lock-файлами:

- `engine.lock.json` — official/PoolSide backend-ы, commit, CUDA-вариант, patch provenance и SHA-256 распространяемых архивов/runtime-файлов;
- `runtime-assets.lock.json` — Python, pip, верхнеуровневые библиотеки и голосовые веса;
- `requirements/*.lock.txt` — точное проверенное Python-окружение;
- `release-manifest.json` — версия проекта и обязательный состав архива.

`UPDATE.cmd` приводит установленную среду к этим одобренным версиям. Чтобы получить новую upstream-версию, сначала выпускается новый архив проекта с обновлёнными lock-файлами и доказательствами совместимости.

## Обычное обновление Александром

1. Закончить текущую задачу Ксении.
2. Оставить достаточно места для резервной копии `llama.cpp` и окружения.
3. При желании выполнить `UPDATE.cmd -CheckOnly`: изменений не будет.
4. Запустить `UPDATE.cmd`.
5. Скрипт зафиксирует активную роль, остановит голос и проверенный процесс модели, создаст запись обновления, применит lock-файлы, выполнит аудит и вернёт прежнюю роль.
6. Если gate не проходит, обновление считается неуспешным и предлагается/выполняется безопасный возврат.

Личные настройки, память, задачи, `workspace` и модели не обновляются и не удаляются.

## Откат

`ROLLBACK-UPDATE.cmd` использует последнюю запись в `runtime/updates`. Он может вернуть сохранённую папку `llama.cpp`, личную конфигурацию и точные Python-пакеты из freeze-файла, затем повторить аудит.

Откат не удаляет более новые резервные копии автоматически. Если после обновления Александр вручную изменил конфигурацию, сначала нужно сравнить её с сохранённой копией, чтобы не затереть полезное изменение.

## Обновление llama.cpp разработчиком

1. Использовать только официальный релиз `ggml-org/llama.cpp`.
2. Зафиксировать номер релиза, commit, точные имена Windows-архивов и SHA-256.
3. Не заменять рабочую папку вручную. Сначала распаковать кандидата в staging и проверить `llama-server --version`.
4. Проверить минимум:
   - запуск и остановку процесса с проверкой PID;
   - chat templates всех включённых профилей;
   - tool calling/Jinja;
   - целевой контекст и объявленный квантованный KV;
   - DFlash/MTP/projector используемых профилей;
   - embedding endpoint;
   - CUDA на целевой видеокарте;
   - полный `AUDIT.cmd`.
5. Записать замеры скорости, VRAM и отличие качества в `docs/AUDIT.md` или отдельный benchmark.
6. Только после этого обновить `engine.lock.json` и собрать новый архив.

Если MTP работает только на определённом commit, более новый номер сборки не является улучшением сам по себе.

### PoolSide и другие локальные backend-ы

PoolSide используется только профилем, который явно ссылается на него в `default.json`. Его нельзя подменять официальным runtime только потому, что оба файла называются `llama-server.exe`. Сначала фиксируются репозиторий, ветка, полный commit, patch и параметры сборки; затем отдельный каталог `bin` проверяется и стадийно устанавливается командой `scripts/install-local-backend.ps1`. Скрипт копирует только перечисленные в lock runtime-файлы, сохраняет прежний каталог и автоматически возвращает его при ошибке переключения. Обычный `UPDATE.cmd` не компилирует fork и не скачивает его из плавающей ветки: если локальный backend расходится с lock, обновление останавливается с точной инструкцией предоставить проверенную сборку.

## Обновление Python-библиотек

1. Создать отдельную временную venv Python 3.12.
2. Изменить одну логическую группу зависимостей, а не всё одновременно.
3. Выполнить импорт, `pip check`, 368+ тестов и живые voice/browser/Windows gates.
4. Снять точный `pip freeze` в `requirements/runtime.lock.txt`.
5. Сверить верхнеуровневые версии с `runtime-assets.lock.json`.
6. Проверить CUDA Torch и faster-whisper на реальном GPU, затем CPU fallback.
7. Обновить документацию и собрать новый архив.

Не используйте незакреплённый `pip install --upgrade` в рабочей среде.

## Обновление моделей

Вес модели не является модулем дистрибутива. Новый GGUF сначала добавляется отдельным выключенным семантическим профилем, проверяется по размеру/SHA-256 и проходит русский benchmark. Рабочий файл не перезаписывается. После допуска меняется декларативное назначение функциональной роли; Python-код и эксплуатационные скрипты не получают условия по названию семейства. Прежний профиль остаётся доступным до завершения приёмки.

Для профиля с закреплёнными `source_repo`, полным commit, именем, размером и SHA-256 используются воспроизводимые команды:

```powershell
python scripts\model-assets.py download candidate
python scripts\model-assets.py verify candidate
python scripts\benchmark-model-candidate.py --profile candidate --acceleration off
python scripts\benchmark-model-candidate.py --profile candidate --acceleration on --acceleration-type draft-mtp --spec-tokens 1
```

Загрузчик не использует пользовательский Hugging Face token, не принимает плавающий revision и после загрузки всегда перечитывает весь файл для SHA-256. Benchmark временно разрешает выключенный профиль только в памяти своего процесса; `config/user.json` и переносимый `enabled: false` не меняются.

## Проверка состояния

- `UPDATE.cmd -CheckOnly` — сравнить установленные компоненты с lock-файлами.
- `HARDWARE-REPORT.cmd` — повторно измерить оборудование после замены GPU/ОЗУ.
- `AUDIT.cmd` — полный локальный gate.
- `runtime/updates` — история попыток обновления и пути резервных копий.
- `runtime/audit/latest.txt` — результат последней полной проверки.

Любая ошибка обновления должна содержать точный этап и путь к записи, а не только сообщение «не получилось».
