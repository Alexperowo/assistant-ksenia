# Модель угроз и защитные границы

## Доверенные и недоверенные стороны

Доверенными считаются локальный код релиза после проверки, lock-файлы, подтверждённые действия Александра и файлы внутри разрешённого `workspace`. Недоверенными считаются содержимое веб-страниц, поисковая выдача, ответы модели, tool arguments, имена/ссылки из интернета и состояние неизвестного процесса.

LLM никогда не является субъектом разрешения: она предлагает действие, а исполнитель проверяет политику независимо.

## Сетевые границы

- LLM и embeddings привязаны только к loopback и защищены локальным ключом.
- LAN-панель — отдельный HTTP-сервис для доверенной домашней сети с PIN, сессией и rate limit.
- LAN нельзя публиковать в интернет; TLS пока отсутствует.
- Browser worker запрещает `file://`, localhost, приватные/link-local IP, `.local` и URL с учётными данными.
- Редирект проверяется до нового соединения.
- Неаутентифицированные чтения создаются без cookies/storage; JavaScript, service workers и WebSocket отключены. Активный browser-control по умолчанию выключен.
- После локального чтения внешний запрос требует подтверждения как потенциальный канал утечки.

## Процессы

- Перед остановкой проверяются PID, полный executable и ожидаемая командная строка.
- Неизвестный владелец порта не завершается.
- Запуск модели имеет bounded timeout; остановка ждёт закрытия process handle и порта.
- Дочерние browser/STT/UIA процессы имеют тайм-ауты и ограниченный протокол stdin/stdout.
- Agent command runner не использует shell, inline-код и не принимает произвольный PowerShell/cmd.

## Файлы и секреты

- Обычные операции ограничены объявленным `developer.workspace_dir` после окончательного разрешения пути; дополнительный корень из личной конфигурации принимается только внутри него.
- Симлинк/relative traversal не должен выводить наружу. Изменяемый путь и GGUF-артефакт отклоняются, если сам конечный объект является символической ссылкой.
- `.env`, credentials, private keys, сертификаты, password databases и похожие имена/расширения запрещены до чтения.
- Секретные файлы не попадают в поиск и RAG.
- Целиковая запись создаёт только новый файл и использует исключительное создание без перезаписи. Существующий исходник меняется только точной заменой с ровно одним совпадением; подтверждение и «Доверенная задача» не ослабляют этот инвариант.
- Изменение и его undo-record создаются под одной межпроцессной блокировкой; постоянные JSON/копии используют уникальный временный файл, flush/fsync и атомарную замену. Отмена имеет резервную копию и hash и не затирает последующую ручную правку.
- Дистрибутив исключает личную конфигурацию, runtime, workspace, модели и ключи.

## Подтверждения

- Безопасное чтение обычно разрешено.
- Запись, удаление, команды, UI, клавиатура, мышь и активный браузер подтверждаются.
- В обычном режиме удаление и отправка сообщения подтверждаются отдельно каждый раз; D-014 является явным предварительным согласием на все подтверждаемые действия только одного запроса.
- Покупка, оплата и перевод запрещены.
- Проверка финансового контекста применяется и к общим средствам ввода.
- Активное Windows/browser-управление по умолчанию выключено. Строка `"false"` и другие не-JSON boolean значения отклоняются, а не интерпретируются как включение. Windows-ввод останавливается fail-closed, если активное или точно заданное целевое окно невозможно идентифицировать.
- Личная конфигурация может сделать действие строже, но не может опустить встроенный минимум `confirm`/`deny`.
- По умолчанию одна задача задаёт не более четырёх самостоятельных вопросов подтверждения; код жёстко ограничивает значение восемью и затем отменяет оставшиеся рискованные действия.
- Александр может локально и вручную подготовить одну «Доверенную задачу». После полного предупреждения и нажатия `1` следующий запрос считается предварительно подтверждённым для действий класса `confirm`; допуск атомарно расходуется одним запросом, действует не дольше 30 минут до начала и не переживает перезагрузку. Активация требует интерактивную консоль, отклоняет перенаправленный stdin, удерживает блокировку `agent-task` и отказывается работать, пока другой запрос выполняется.
- Доверенный режим не может быть включён поддерживаемым инструментом модели, веб-контентом, голосовой фразой или LAN-панелью. Ошибка и отмена также расходуют допуск. Решения `deny`, финансовый запрет, секретные пути, файловая область встроенных инструментов, защищённые процессы и сетевые фильтры не ослабляются.

Нельзя ослаблять подтверждение потому, что «модель уверена» или задача сформулирована голосом. Единственный поддержанный способ предварительного согласия — D-014 с физическим локальным вводом пользователя.

`DeveloperRunner` теперь по умолчанию использует backend `disabled`: подтверждение действия или «Доверенная задача» не запускают Python, Node, Git, npm либо тесты без отдельного execution backend. Неизвестная и повреждённая конфигурация блокируется до создания процесса. Это закрывает прежний молчаливый запуск недоверенного кода с правами пользователя, но ещё не реализует полезную ОС-песочницу.

Legacy-backend `unsafe_host` сохранён только для ручной диагностики и требует точной строки признания риска. Его проверки программы, аргументов, `workspace`, времени и вывода полезны, но не являются системной границей: запущенный код получает права учётной записи Windows. Предварительная оценка Microsoft Execution Containers 0.8.0 показала рабочее ограничение файлов и сети обычным AppContainer, но upstream прямо запрещает считать preview-профили security boundary; поэтому MXC не включён в production. Целевой backend обязан отдельно ограничить файловую систему, сеть, дерево процессов, CPU/RAM, время, окружение и UI, а Permission Broker остаётся снаружи.

Аудит 30 августа подтвердил внешний blocker production backend-а на компьютере Александра: AMD-V/SVM выключен в UEFI, гипервизор не активен, WSL и container runtime отсутствуют. Поэтому Windows Sandbox/Hyper-V нельзя принять без изменения firmware и перезагрузки. Нативный AppContainer является системной границей, но самостоятельный launcher ещё не прошёл полный fault-injection набор; новый `CreateProcessInSandbox` документирован Microsoft как experimental. Job Object без AppContainer/VM ограничивает ресурсы и дерево процессов, но не файлы и сеть. Подробности и критерии допуска находятся в `SANDBOX-AUDIT.md`.

## Live и акустическая граница

Live не расширяет полномочия: tool calls по-прежнему проходят обычные схемы, Permission Broker и TaskControl. Прерывание сначала выставляет cancellation event, чтобы прекратить будущую генерацию и checkpoints инструментов, и лишь затем очищает аудио. Уже начатый внешний эффект может требовать собственной кооперативной отмены; остановка голоса не означает автоматического отката завершённого действия.

Сгенерированный ответ нельзя считать озвученным. Журнал хранит полный `generated_answer` отдельно от `spoken_answer`, а в диалоговую память попадает только подтверждённый непрерывный префикс завершённых фраз. Событие начала playback, текущая частичная фраза, отменённая очередь и поздний callback не подтверждают речь. Диагностика записывает размеры и исходы, а не содержимое Live-фраз.

Пока не подключён и не принят AEC, `live.enabled` остаётся выключенным. Одновременное прослушивание динамиков без подавления эха создаёт не только неудобство, но и логическую петлю: собственный TTS может вызвать ложное прерывание или новую команду. Full-duplex нельзя объявлять безопасным по одним unit-тестам.

## Диагностика и приватность

Журнал хранит тип события, компонент, длительность, размеры и безопасные исходы. Он не должен хранить полный запрос/ответ, вводимый текст, содержимое файла, PIN, пароль, API key, параметры URL или полную команду. Новое поле диагностики проходит `safe_value` и отдельный тест утечки.

## Supply chain

- Python installer проверяется Authenticode и издатель.
- Архивы `llama.cpp`, Vosk и известные веса speech pack проверяются SHA-256.
- Каждый GGUF перед первым runtime-запуском проходит размер и полный SHA-256. Cache доверяется только при полном совпадении канонического пути, file identity, размера, временных меток и ожидаемого хэша; изменившийся файл перечитывается.
- Python-версии фиксируются lock-файлами.
- `pip`, `setuptools` и Torch закреплены на проверенных версиях; CUDA index хранится в lock-конфигурации и обязан указывать на официальный HTTPS-хост PyTorch.
- Сторонние GitHub Actions закреплены полным commit SHA проверенного официального релиза, а не плавающим major-тегом.
- Новая upstream-версия сначала считается кандидатом, а не автоматическим обновлением.
- Release archive получает собственный список SHA-256 и машинную проверку запрещённых файлов.
- Сборщик по умолчанию отвергает грязное Git-дерево, чтобы в ZIP не попала непроверенная смесь состояний. `-AllowDirtySource` предназначен только для явно помеченной локальной диагностики, не для выпуска.

Оставшийся риск: версии Python-зависимостей закреплены точно, но wheel-файлы пока не снабжены собственными SHA-256 в репозитории. Установщик ограничивает Torch официальным HTTPS index, а остальные зависимости — lock-файлом, однако полностью автономному офлайн-релизу всё ещё нужен собственный подписанный wheelhouse с хешами и отдельная проверка лицензий.

## Реакция на подозрительное поведение

1. Остановить голос `Control + Alt + S`.
2. Не завершать неизвестный процесс по одному номеру порта.
3. Сохранить время и безопасные журналы.
4. Отключить сеть, если есть риск внешнего действия.
5. Запустить аудит из доверенного дерева.
6. Сравнить бинарники/архивы с lock-файлами.
7. Не очищать доказательства до диагностики.
