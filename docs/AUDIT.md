## Дополнение 7 сентября 2026 — управляемое ожидание completion headers

Исходная точка: `280a637`. Настоящий временный loopback HTTPServer подтвердил
четыре отказа старого completion-пути: отмена до заголовков ждала сервер 2,032 с;
чтение тела HTTP 503 — 2,016 с; pre-cancel всё равно отправлял POST; 302 приводил
к попытке перехода на другой endpoint. Тестовые запросы не содержали личных данных,
серверы принадлежали проверке. Внешние адреса не использовались.

`complete_chat(checkpoint=...)` получил private loopback socket до connect/send,
проверку отмены при ожидании headers и передачу ответа прежнему SSE parser.
Первый вариант с одним socket.shutdown не прошёл Windows cleanup-test: reader
оставался активным до ответа сервера. Он не принят. Принятый `RawIOBase` adapter
владеет duplicate socket handle, опрашивает recv с интервалом 50 мс и сохраняет
частичные строки через BufferedReader; HTTP framing по-прежнему выполняет
`http.client.HTTPResponse`. Исходный idle timeout сохраняется. Протокольные API:
[HTTPConnection/HTTPResponse](https://docs.python.org/3/library/http.client.html)
и [socket](https://docs.python.org/3/library/socket.html). Новых зависимостей нет.

В управляемом пути pre-cancel запрещает отправку, proxy/redirect исключены,
HTTP error body не читается; журнал различает reader `connect_headers`/`body`.
Девять новых тестов покрывают десять последовательных header-cancel с нулевыми
active/stuck counters, header deadline, частичные заголовки с паузами, отмену
после первого токена, SSE, HTTP 503, redirect, proxy и запрет remote endpoint.

Полный gate: exit 0, 484/484 и shuffled 17/73/211 без ошибок/пропусков/warnings;
release/dependencies/Doctor/LAN и Silero→Whisper CUDA (`landmark_recall=1.0`).
Для настоящей проверки временно запущен UI-Mate `ui_butler/ui_fast`, PID 7876:
`test_active_model.py` прошёл именно новый completion-путь (ответ «Ксения»,
0,734 с, context 16384). Штатный отдельный stream cancellation gate также прошёл:
отмена назначена на 500 мс, возврат/cleanup 532 мс, active/stuck readers 0.
Последний gate проверяет существующий `stream_chat`, не имитирует зависшие headers.
RAG остаётся выключенным и явно пропущен. После gate остановлен только проверенный
собственный PID 7876; запущенных моделей осталось 0. Личная конфигурация не менялась
(SHA-256 `9E3F6CCD5098877B787548F26612098A57444F7DDEBA0136230588DAD74ED223`).
Копия отчёта: `runtime/audit/checkpoints/2026-09-07-reliability-start/after-c1-completion-headers.txt`.

Границы: общего research budget ещё нет. Native fault-тесты здесь проверяют
headers/body, не все connect/send условия. `complete_chat` без checkpoint,
`stream_chat` и tokenizer сохраняют прежний opener; для них pre-header/proxy/
redirect-контракт требует отдельного аудита. `localhost` нового пути закреплён
за IPv4 loopback; IPv6 требует явного адреса и отдельной проверки URL-builder.
Непрерывный Live, фоновые задачи и пользовательская приёмка не завершены.

## Дополнение 7 сентября 2026 — отменяемый DNS read-only страницы

## Дополнение 7 сентября 2026 — причины отказа поиска, C1 частично

Исходная точка: `c05ad26`. Подтверждено тестами, что ошибочный результат
`browser_search` ошибочно запускал уточняющий повтор и затем становился сообщением
о ненайденных источниках. То же происходило при `denied`, `confirmation_required`
и повреждённом payload. Теперь уточнение выполняется только после корректных
успешных ответов поиска; отказ инструмента/политики не запускает этот второй раунд.
Успешные источники другого параллельного запроса не отбрасываются.

`ResearchError(ChatError)` содержит фиксированный код и безопасную фразу:
`search_unavailable`, `no_sources`, `denied`, `confirmation_required`.
Голосовой интерфейс использует эту фразу без внутренних URL/исключений.
Общий `ToolResult.status=error` не позволяет честно различить DNS, timeout,
сломанный browser runtime и другие причины, поэтому сообщение говорит
«Поиск сейчас не сработал», а не утверждает, что интернет точно отключён.
Подтверждения не обходятся; автоматический запрос approval из research этим
изменением не добавлен. Перед каждым новым tool-вызовом проверяется cancellation.

Добавлены семь research-тестов и два сценария продолжения CLI/voice после
типизированного отказа. Тестируются ошибочный/пустой/повреждённый ответ, policy
refusal, отказ уточняющего повтора, частичный успех и отмена перед повтором.
Управляемая ошибка не требует ждать настоящего сетевого тайм-аута. Отдельный
настоящий `BrowserReader` search по публичной документации вернул 10 результатов
за 2,875 с; это один smoke, не benchmark Google News или SLA.

Общий deadline исследования и mid-operation cancellation браузера ещё не готовы.
Это исправление убирает лишний последовательный раунд при отказе, но не сокращает
тайм-аут уже выполняющегося запроса. Непрерывный Live и фоновые задачи не менялись.
Повторный полный `check.ps1` завершился с кодом 0: 462/462 теста и порядки
17/73/211 без ошибок/пропусков/warnings, release/dependency/Doctor/LAN и
Silero→Whisper CUDA (`landmark_recall=1.0`). Active LLM/cancellation пропущены
из-за отсутствия запущенных моделей; RAG выключен. Отчёт: `runtime/audit/latest.txt`,
контрольная копия: `runtime/audit/checkpoints/2026-09-07-reliability-start/after-c1-search.txt`.

## Performance baseline

Добавлен лёгкий Performance / Acceptance Harness поверх существующего безопасного JSONL. Один `trace_id` проходит через STT, orchestrator/agent, LLM, TTS, LAN и cancellation; содержимое реплик, файлов и секреты не записываются. Отчёт считает min/average/p50/p95/max, строит waterfall по milestones и явно показывает неполные трассы. Контракт и ограничения описаны в `docs/PERFORMANCE.md`.

Контрольный активный запрос 29 августа 2026 года, trace `8ace28a8f87b46588cdaff7109344c55`:

- профиль `generalist`, Laguna/PoolSide, фактический контекст 98304;
- prompt 62 токена, completion 4 токена, ответ «Ксения»;
- `llm_first_token`: 1969 мс;
- `llm_generation_end`: 2063 мс;
- трасса содержит все три требуемые для этого LLM-smoke milestones;
- после теста сервер остановлен, `runtime/state.json` отсутствует.

Это одиночный acceptance-smoke, а не статистический benchmark. Значения p50/p95 становятся репрезентативными только на корпусе повторов. Streaming-запрос явно просит OpenAI-compatible usage; если backend его не возвращает, токенные метрики остаются отсутствующими, а не записываются фиктивным нулём.

Живой голосовой ход 1 сентября выявил другое, пользовательски критичное поведение: микрофон и STT закончили работу быстро, но новая Laguna оценивала холодный полный tool prefix более минуты. Парный A/B на 16K/96K подтвердил почти одинаковый cold TTFT около 64 с и warm TTFT 1,66–1,85 с при 2221 повторно использованном token. Поэтому уменьшение максимального контекста отклонено как лечение этой задержки. Минимальное исправление выбирает стабильный `CHAT` без tool schemas для короткой реплики, которая не просит внешнего действия; action/research/developer routes не меняются.

### HTTP cancellation baseline

Первый живой cancellation-gate обнаружил подтверждённую задержку: checkpoint должен был отменить длинную генерацию через 500 мс, но синхронный `HTTPResponse.close()` удерживал поток около 1437 мс, и `llm_actually_cancelled` появился только через 2016 мс. После socket shutdown и асинхронного cleanup три последовательных повтора дали 578, 657 и 500 мс до исключения отмены. Во всех трёх случаях `active_reader_threads=0` и `stuck_reader_threads=0` после cleanup; процесс модели и порт затем штатно освобождены.

Это подтверждает transport cancellation. Последующий Tour One M3 тест уже подтвердил слышимую остановку и продолжение с перебивающей реплики; точная пара `interrupt_detected → audio_actually_stopped` остаётся метрикой длинной 20–30-turn серии, а не неизвестностью самого маршрута.

### Tool lifecycle и cooperative cancellation

Состояния вызова инструмента формализованы как `PLANNED`, `APPROVED`, `STARTED`, `COMPLETED`, `FAILED` и `CANCELLED`. События связаны отдельным `tool_execution_id`, сохраняют номер попытки и различают отказ политики, отказ пользователя, отмену при подтверждении и отмену во время выполнения. После подтверждения dispatcher начинает новую попытку с тем же идентификатором исполнения.

`TaskControl.checkpoint` теперь передаётся в `ToolExecutor`; поиск по workspace и индексирование/поиск RAG проверяют его между файлами и при длинном переборе векторов. Это подтверждённое улучшение, но статус остаётся **PARTIAL**: один блокирующий вызов embedder, браузерный subprocess, Windows/UI Automation и legacy `unsafe_host` пока не гарантируют mid-operation cancellation. Для процессов такую гарантию должен дать Sandbox Worker с управлением деревом дочерних процессов. Уже физически завершённые действия не считаются откаченными.

## Конфигурация без явного хардкода

Правило проекта теперь формализовано так:

1. `capability_roles` описывает функции: `assistant`, `researcher`, `developer`, `heavy_brain`.
2. `models` содержит сменные семантические профили; назначенные `generalist`/`reasoning` отделены от выключенных кандидатов.
3. `artifacts` описывает роли файлов `model`, `draft`, `projector` независимо от семейства.
4. `paths.models_dir` и `paths.model_search_dirs` задают локальные корни. Личные абсолютные пути разрешены только в исключённом из Git `config/user.json`.
5. Python-ядро строит команду исключительно из типизированного профиля. Ни оркестратор, ни CLI, ни Doctor не ищут слова в имени модели.
6. PowerShell разрешает Python из явного параметра, `KSENIA_PYTHON`, личной конфигурации, активного venv, project-local venv или переносимого LocalAppData-каталога. Фиксированных путей дисков больше нет.
7. Точные имена и SHA-256 в `default.json` — не логический хардкод, а декларативный supply-chain lock. Они не влияют на алгоритм выбора поведения.

Дополнительно исправлено сохранение путей: прежняя команда могла заменить весь `config/user.json`. Теперь обновляется только `paths`, запись атомарна, а голос, браузер, поисковые каталоги и другие личные настройки сохраняются.

`live.enabled` остаётся `false` в переносимой конфигурации. До обычного default остаётся серия 20–30 ходов, паузы внутри мысли и проверка другого акустического тракта с измеримым эхом.

Затем добавлен opt-in PCM far-reference: output stream публикует принятые 10-мс кадры в тот же worker, где закреплённый `pywebrtc-audio` применяет AEC3/NS. Три последовательных AEC handshakes, строгий Xenia playback и stop за 7,2 мс зелёные. Акустическая величина echo reduction пока не измерена; подробности в `docs/AUDIO-FULL-DUPLEX-AUDIT.md`.

## Песочница и разрешения

Permission Broker остаётся главной границей полномочий. Модель не может повысить разрешения, активировать доверенную задачу, вывести встроенные файловые инструменты за `workspace`, завершить неизвестный процесс или разрешить финансовое действие.

Запуск Python/Node/Git/npm по умолчанию закрыт: `developer.execution.backend = disabled`. Legacy `unsafe_host` требует точного локального признания риска и не является песочницей. Production-grade Sandbox Worker с файловыми, сетевыми, процессными, CPU/RAM/time limits всё ещё главный незакрытый security-приоритет.

30 августа read-only capability probe подтвердил, что на компьютере Александра выключена аппаратная виртуализация (`VirtualizationFirmwareEnabled=False`), hypervisor отсутствует, WSL и container runtime не установлены. Поэтому Windows Sandbox/Hyper-V worker заблокирован до отдельного изменения UEFI и перезагрузки. AppContainer является реальной системной границей, но ни MXC preview, ни experimental `CreateProcessInSandbox`, ни один Job Object не приняты вместо production backend. Полная матрица и fault-injection acceptance находятся в `docs/SANDBOX-AUDIT.md`.

### Реальная проверка модуля разработки

Модуль проверялся на чистой staging-копии Android-проекта FUTO Keyboard, а не только моками. Динамическая процедура разработки, общий предел tool-вызовов, предпочтение поиска перед обходом каталогов и блокировка сырой tool-разметки отработали как задумано. При этом экспериментальное скрытие инструментов чтения после фиксированного числа вызовов выявило опасное поведение модели: Laguna сохранила намерение «прочитать», но выбрала оставшийся `write_workspace_file` и попыталась записать короткий маркер в четыре существующих Kotlin-файла и один новый неверный путь.

Журнал изменений позволил отменить все пять операций в обратном порядке. После восстановления `git status --short` и `git diff --check` целевого проекта были чистыми, а ошибочно созданный файл отсутствовал. Это доказало полезность журнала, но также показало, что динамически убирать схемы инструментов под моделью небезопасно. Эксперимент полностью удалён: состав инструментов остаётся стабильным на протяжении задачи.

Дополнительно `write_workspace_file` теперь имеет узкий контракт create-only. Существующий путь получает `existing_file_requires_replace` и остаётся неизменным даже после подтверждения; для исходников разрешена только точная замена с одним совпадением. Текущую Laguna пока нельзя считать принятым автономным исполнителем сложной разработки без надзора. Следующее усиление должно быть структурным — проверяемый patch/набор разрешённых путей и валидация diff — а не новым prompt-only ограничением.

## Память и RAG

Сохраняются SQLite + WAL + FTS5 + embeddings + cosine + RRF, цитаты до строк, стабильный порядок, порог семантического совпадения и явный `no_match`. Отдельная векторная БД сейчас не нужна.

Следующее недорогое улучшение — reranker: lexical/vector top-20 → компактный reranker → top-5. Его нельзя добавлять без постоянного русского набора запросов и сравнения качества/задержки.

В свободное GPU-окно, не затрагивая AgentZero:

2. Полностью проверить размеры/SHA-256 артефактов через `model-assets.py verify`.
3. Для `generalist` дополнить уже зелёный 96K/DFlash/chat gate настоящим tool-calling и более длинным benchmark скорости/VRAM.
4. Для `reasoning` дополнить уже зелёный 96K/MTP/mmproj/chat gate планом, tool schema, тестовым image-input и при необходимости MTP on/off A/B.

6. После tool/vision/RAG-проверок считать весь модельный слой принятым, не смешивая это с уже доказанной совместимостью runtime-профилей.
