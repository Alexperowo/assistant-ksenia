# Данные, форматы и миграции

## Классы данных

Переносимый код и пользовательские данные разделены. `config/default.json`, lock-файлы и процедуры входят в релиз. `config/user.json`, `runtime`, `workspace`, browser profile и модели принадлежат конкретной установке и сохраняются при обновлении.

## JSON-состояние

### `runtime/state.json`

Содержит PID, роль, executable, путь к модели, время запуска, launch signature, запрошенный/фактический контекст и журнал процесса. Файл не доказывает, что процесс ещё тот же: PID и полный executable проверяются через Windows перед использованием.

### `runtime/tasks/<id>.json`

Поля задачи: `id`, `request`, `channel`, `state`, `status`, `answer`, `error`, `confirmation`, `resumable`, `owner_pid`, timestamps, `events` и вычисляемый `done`. Состояния: queued, planning, running, waiting_confirmation, paused, verifying, completed, failed, cancelled, interrupted.

Запись идёт во временный `.tmp` и заменяет целевой файл. После аварии живая задача становится interrupted. Текст задачи является пользовательским и не входит в релиз.

### Прочие JSON

- `runtime/memory/session.json` — недавняя история и сжатая сводка.
- `runtime/voice/agent.json` — проверяемый процесс голосового режима.
- `runtime/hardware/latest.json` — read-only снимок оборудования и рекомендация.
- `runtime/updates/*/metadata.json` — резервные копии и состояние обновления.
- `PACKAGE-MANIFEST.json` — SHA-256 файлов конкретного ZIP; не является runtime-данными.

JSON пишется через временный файл и replace, но без отдельного `fsync`. При внезапном отключении питания возможна потеря последней операции; предыдущие долговечные данные не должны очищаться автоматически.

## SQLite

Все постоянные базы используют WAL и `synchronous=FULL`; аудит запускает `PRAGMA quick_check`.

### `knowledge.sqlite3`

Таблица `knowledge`: id, исходный текст, уникальная нормализованная форма, категория, источник, created/updated timestamps. Запись появляется только после подтверждения Александра.

### `handoffs.sqlite3`

Таблица `handoffs`: id, task_id, role, kind, content, metadata_json и created_at; индекс `(task_id, id)`. Это последовательный журнал плана, ошибок и результата между моделями.

### `rag.sqlite3`

- `documents`: namespace, path, SHA-256, размер, modified_ns, embedding model и indexed_at.
- `chunks`: document id, path, номер, диапазон строк, текст, float-vector BLOB и размерность.
- `chunks_fts`: FTS5 external-content с триггерами insert/update/delete.

RAG является восстанавливаемым индексом. При несовместимой embedding-модели безопаснее переиндексировать исходные файлы, чем преобразовывать старые векторы.

## Журналы

`diagnostics.jsonl` — одна UTF-8 JSON-запись на строку. Обязательные поля: UTC time, session id, sequence, uptime, PID/thread, level, component и event. Чувствительные значения заменяются длиной и коротким SHA-256. Журнал ротируется; повреждённая строка не должна ломать чтение остальных.

`tool-events.jsonl` и журналы `llama-*.log` имеют более узкое назначение. Не копируйте их в публичный архив, даже если основная диагностика очищена.

## Резервное копирование

Для согласованной ручной копии:

1. Остановить голос и завершить активную задачу.
2. Безопасно остановить модель; embedding server должен быть закрыт.
3. Скопировать `config/user.json`, `runtime/memory`, `runtime/tasks`, `workspace` и при необходимости browser profile.
4. Для SQLite при работающем процессе копировать базу вместе с `-wal`/`-shm` нельзя считать полноценной стратегией; предпочтительна остановка или SQLite backup API.
5. Проверить хеш/размер резервной копии и возможность чтения, прежде чем удалять источник.

Модели хранятся отдельно и обычно восстанавливаются из известного репозитория по SHA-256.

## Правила миграции

1. Никогда не менять схему только «на месте» без версии и теста старых данных.
2. До первой несовместимой миграции добавить таблицу/поле schema version.
3. Миграция создаёт резервную копию, работает транзакционно и допускает повторный безопасный запуск.
4. Сначала поддерживается чтение старого формата, затем запись нового; удаление обратной совместимости — отдельный релиз.
5. RAG можно перестроить. Knowledge, handoff, задачи и подтверждения нельзя молча сбрасывать.
6. Миграция проверяется на копии реальных обезличенных данных и на искусственно прерванном запуске.
7. Результат и способ отката описываются в CHANGELOG и `docs/MAINTENANCE.md`.

Сейчас таблицы создаются аддитивно через `CREATE IF NOT EXISTS`; несовместимых миграций ещё не было.
